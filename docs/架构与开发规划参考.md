## 一页速览

| 决定 | 做法 |
|---|---|
| 技术栈 | .NET 10 + C# + WPF；SQLite（Microsoft.Data.Sqlite 自带引擎，FTS5 全文索引）；xUnit |
| 分层 | **Core**（纯规则，无 IO）← **Infrastructure**（读文件、数据库、设置、系统接口）← **App**（WPF 窗口与视图模型） |
| 数据边界 | 对别的程序的数据**只读**；自己写的东西只在**一个数据根目录**（默认 `D:\<产品>Data`） |
| 只加不减 | 来源删了、挪了，自己这一行和一份副本照样留着；只有用户在本程序里删除才删 |
| 数据库 | 目录库（含用户偏好与删除墓碑）+ 可重建的派生库（全文索引、统计账本）各一个文件、各一把锁；来源记录的副本放 `archive\` |
| 导入 | 用户手动导出的归档包（如 Google Takeout）：只读用户选中的文件，复制进数据根目录再读，重复导入只补新增 |
| 后台工作 | 增量（只读变化的部分）、独立低优先级线程（Windows 后台模式）、一个接一个跑、可取消、不在用户操作时重排界面；第一次打开先列最近的一批 |
| 质量 | 每个规则有单元测试，每个修复有回归测试并做反向验证；界面在内存里渲染核对；目标规模的合成数据与泄漏测试；发布前冒烟 |
| 发布 | 自用：多文件 self-contained；分享：单文件 exe + 带使用说明的 zip；公开：GitHub 仓库（MIT）+ Release |
| 文档 | README 每个版本一节写实测数字；使用说明给最终用户；capabilities 写技术细节 |

## 二、适用的软件类型

**适合**：

- Windows 本机运行、单用户、不需要联网；
- 核心工作是「读别处产生的数据 → 建自己的目录和索引 → 列表、搜索、查看、统计、导出 → 交给外部程序打开」；
- 条目从几百到几万条，原始文件从 KB 到 GB 级，可能正被别的程序写入，也可能被别的程序清理掉；
- 数据也可以来自用户手动导出的归档包（云端服务的导出，如 Google Takeout）：导入一次，以后只补新增。

**典型例子**：实验 / 田间调查数据管家（病级、株高、穗部性状记录的整理、检索、汇总、导出）；分析结果浏览器
（GWAS 结果、流水线输出、日志）；文献 / PDF / 图片的本地资料库；某个软件的历史记录与项目管理器
（就像会话管家之于 Claude、ChatGPT 和 Gemini）。

**不适合**：多人实时协作、必须有服务器、手机端、重图形。需要跨平台时保留 Core / Infrastructure 的分法，
只把 App 层换成 Avalonia、MAUI 或网页。

## 三、总体架构

```
┌──────────────────────────── App（WPF，net10.0-windows）─────────────────────────────┐
│ App.xaml.cs   启动：单实例、无界面模式、主题、崩溃提示；自己创建主窗口（不用 StartupUri）   │
│ 窗口          主窗口（工具栏 / 筛选栏 / 列表 / 详情 / 状态栏）、阅读窗口、统计窗口、对话框    │
│ ViewModels    状态、搜索防抖、可取消的加载、数据库调用门（SemaphoreSlim）、后台调度         │
│ Ui 服务       AppSettings（延迟保存）、Theme、TrayIcon、GlobalHotkey、TaskbarJumpList、   │
│               MemoryRelief、WindowPlacementMemory、BackgroundMode、ThrottledProgress；     │
│               Themes/Dark.xaml（全部颜色的命名令牌）                                      │
└──────────────────────────────────────┬────────────────────────────────────────────────┘
                                       │ 只依赖下层
┌──────────────────────────── Infrastructure（net10.0-windows）────────────────────────┐
│ Paths / Safety / Migrator   数据根目录解析、写入白名单、旧目录迁移                       │
│ Discovery                   找到已安装的程序与数据位置（用系统接口，不启 PowerShell）      │
│ Readers（Backends）          每种数据格式一个读取器：只读、流式、容错                     │
│ Catalog                     SQLite 目录 + 增量同步（读、写分两步）+ 键集分页 + 偏好与撤销   │
│ Archive                     来源记录的副本（zstd 可寻址压缩、按位置直读），来源没了改读副本  │
│ Import                      用户选中的导出包：复制进数据根目录再读，重复导入只补新增         │
│ Search                      FTS5 全文索引（trigram，中文子串）                          │
│ Ledger                      增量统计账本                                              │
│ Settings                    设置记录 + Sanitize + 原子写；小规则类（如 SearchHistory）     │
│ Launch / Export             打开外部程序与深链接；Markdown / 自包含 HTML / CSV 导出        │
└──────────────────────────────────────┬────────────────────────────────────────────────┘
┌──────────────────────────── Core（net10.0，纯逻辑，无 IO）────────────────────────────┐
│ Contracts  稳定键与不可变记录    Rules  排序、分组、可见性、覆盖率    Display  相对时间、路径缩写、Markdown │
└───────────────────────────────────────────────────────────────────────────────────────┘
tests/UnitTests         → Core 与纯规则，几百毫秒跑完
tests/IntegrationTests  → 临时目录里造真实格式的文件和 SQLite，几秒跑完
```

**依赖规则**

- 只向下依赖：App → Infrastructure → Core。Core 不碰文件、注册表、时钟（「现在」作为参数传入）。
- 能写成纯函数的规则一律放进可测的静态类（Core 的 Rules，或 Infrastructure 里的 `SearchHistory` 这类），
  界面只决定「什么时候调用」。
- 每个外部数据源一个 Reader，Reader 只产出 Core 里的记录类型；同步服务负责合并、去重、折叠。
- 派生数据（目录、索引、账本）各用一个 SQLite 文件和一把锁；除目录库外，删掉任何一个都能自动重建。

**目录结构**

```

├─ src/<Project>.Core/             Contracts/  Catalog(Rules)/  Display/
```

## 四、十一条设计原则

1. **对别人的数据只读。** 打开外部文件一律 `FileAccess.Read` + `FileShare.ReadWrite | FileShare.Delete`
   （对方正在写也能读，也不妨碍对方删改）。要「改」的东西——置顶、改名、备注、分组、归档——只存在自己的库里，
   源程序里的永远不变。用集成测试证明：读前读后外部文件的哈希和修改时间不变。
2. **只加不减。** 来源程序清理、删掉或挪走了自己的记录，目录里这一行照样留着（标「原记录已删」），并且早就在
   自己的数据根目录里存了一份副本，查看、搜索、导出都改读副本。同步发现来源里没有了只做标记，从不删行；
   只有用户在本程序里明确删除才删（连同副本和索引里的内容），并记一条墓碑，以后同步不再列出。来源被别的工具
   压缩了（如 `.jsonl.zst`）也要能读回。「来源里没有了」不等于「用户想删」。
3. **自己的数据只在一个根目录。** 默认 `D:\<产品>Data`（会增长的数据不放系统盘），不可用时退回
   `%LOCALAPPDATA%\<产品>`；旧位置的数据先复制、逐个校验、再删旧的，任何一步失败都原样不动。所有写入经过
   `PathPolicy`：拒绝写进外部程序的目录、驱动器根、用户主目录根。环境变量 `<PRODUCT>_DATA_DIR` 可指定根目录，
   专给测试副本用。
4. **证据先于能力。** 每项能力在能力矩阵里标 **Verified**（真机实测过）/ **Implemented**（有自动测试）/
   **Unknown**（没验证）/ **Unsupported**（对方没有这个概念）。Unknown 的能力不许用「空实现返回成功」糊过去。
   开工前先写只读探测脚本，把每个数据源的真实情况落成 `evidence/*.json`。
5. **能不写就不写。** 会改写外部数据的功能要先过门禁：用可丢弃的数据在真实环境实测通过，才能打开；
   过不了就不交付，并在界面和文档里说明原因。本项目的「原生归档」整条链路就是因此删掉的。
6. **失败要便宜。** 设置坏了按默认值启动（`Sanitize` 丢掉不合理的值）；设置先写 `.tmp` 再原子替换；派生库
   坏了或格式版本变了就重建；单个文件读失败就跳过、下次再试；后台任务出错不弹窗、不影响主列表；
   界面上未处理的异常给一个说明对话框，无界面模式写 `_crash.txt`。
7. **增量、后台、可取消。** 只读变化了的文件；只追加的文件从上次的偏移接着读；没变化就不写库。重活放在独立的
   低优先级线程上一个接一个跑；界面上的每次查询都可被下一次取代；搜索输入防抖。第一次打开先列最近的一批，
   其余后台补齐，不让用户对着空列表等全部读完。
8. **不打扰用户。** 自动刷新等用户停手（指针刚动过、按着鼠标、菜单或下拉开着都算忙）才重排列表，并保留选中与
   滚动位置；整理操作给「撤销」；结果写在状态栏，不弹窗；空列表说明原因并给出下一步；不抢焦点，不自己跳到前台。
9. **键盘优先、可访问。** 常用操作都有快捷键并在 F1 列出；Esc、Enter、↓ 的含义处处一致；控件都有
   `AutomationProperties.Name`；状态变化通知读屏软件；尊重系统「关闭动画」；每显示器 DPI。
10. **先测量再优化，结论写成数字。** 新旧两版同一时间并排比，数字写进 README 的实测表；规模问题用目标规模的
    合成数据量（几百条时看不出的 O(n²)，几千条时就是十几秒）。
11. **文档诚实。** 写清改了什么、实测多少、哪些没做到、哪里偏离了计划（例如「这一轮测试是后补的」）。

## 五、各层的标准模块（照搬清单）

### Core

| 模块 | 职责 | 本项目里 | 要点 |
|---|---|---|---|
| Contracts | 稳定键、不可变记录 | `ConversationKey(backend, account, org, nativeId)`、`SessionMetadata` | 键在所有来源间唯一且永不变；`record` + `init` |
| 来源登记 | 每个来源叫什么、排第几、能做什么 | `Sources`、`SourceInfo`、`AppFamily` | 名字、颜色、排序、打开 / 续接 / 改动 / 副本 / 用量的做法都写在一条登记里，各处只读它；排序 SQL 由登记生成；加一个来源 = 登记一条 + 读取器 + 同步里一行，测试核对每个来源都登记了 |
| Rules | 排序、分组、可见性、覆盖率 | `OrderingRules`、`GroupRules`、`ViewArchiveRules`、`SourceCoverageRules` | 全部单元测试 |
| Display | 只为显示的纯函数 | `RelativeTime`、`PathDisplay`、`Markdown`（+Html）、`ContinuationNames` | 「现在」作为参数 |

### Infrastructure

| 模块 | 职责 | 本项目里 | 要点 |
|---|---|---|---|
| 路径 | 解析数据根目录与各子目录 | `LauncherPaths` | 环境变量 → 首选 → 回退；解析一次、全程不变 |
| 安全 | 写入白名单 | `PathPolicy` | 每条拒绝规则一个测试 |
| 迁移 | 旧根目录搬到新根目录 | `DataRootMigrator` | 复制 → 校验 → 删旧 |
| 发现 | 已安装程序与数据位置 | `WindowsAppDiscovery`、`InstallVariants` | 用包管理接口：约 2 s → 首次 49 ms、之后 6 ms |
| 读取器 | 每种格式一个 | `CliMetadataReader`、`DesktopCodeMetadataReader`、`CodexMetadataReader`、`GeminiMetadataReader`、`TranscriptReader` | 1 MB 块读、按换行切；长行先看开头；半行不读；坏行跳过 |
| 探测缓存 | 读过的文件头存盘 | `CliProbeCache`（`probe-cache.json`） | 按（长度, 修改时间）复用；读法规则一改就升 `ProbeRules` 作废整份 |
| 目录 | SQLite 目录 + 同步 | `SqliteCatalog`、`CatalogSyncService`、`CatalogSchema.sql` | WAL、`busy_timeout`；键集分页；修订号；同步分 `Read`（不持锁）与 `Apply`（持锁）；来源没了 `MarkGone` 只标记；用户删除写墓碑 |
| 副本 | 来源记录的副本 | `TranscriptArchive`、`PackedCopy`、`TranscriptFiles`、`TranscriptLocator` | zstd 可寻址格式：约 32 MB 一帧、在换行处切、帧尾一张寻址表，读的人按位置只解一帧、当原文件读；只追加新增的完整行（先比对末尾哈希，写失败原样写回）；旧的明文副本压好后整份解压核对才删；只在自己的文件夹里写和删；找不到来源时回落到副本 |
| 导入 | 用户选中的导出包 | `GeminiTakeout`、`GeminiTakeoutStore`、`HtmlMarkdown`；`ExportPackage`、`ChatGptExport`、`ClaudeExport`、`WebExportStore` | 先复制进数据根目录再读；JSON / HTML 两种格式算出同一个键，重复导入只补新增；几百 MB 的导出逐段流式读；树形的对话只取当前分支；再导入只补新增、更新变过的，从不删；内容不变的文件不重写；可整批移除 |
| 搜索 | 全文索引 | `ContentIndex`（FTS5 trigram）、`SearchKeys` | 三字以上走索引、两字扫描；NFKC + 小写归一 |
| 账本 | 增量统计 | `UsageLedger`、`UsageScanner` | 记文件偏移与状态续读；同一事件只算一次 |
| 设置 | 偏好与小规则 | `SettingsStore`、`LauncherSettings`、`SearchHistory` | `Sanitize`；原子写；损坏读默认 |
| 启动外部 | 打开外部程序、深链接 | `ClaudeDeepLink`、`ChatGptLauncher`、`QuickOpen` | 链接参数白名单校验，拒绝一切不合格式的 |
| 导出 | Markdown / HTML / CSV | `SessionExporter`、`TranscriptExport` | HTML 自包含，不加载远程资源 |

### App

| 模块 | 职责 | 本项目里 | 要点 |
|---|---|---|---|
| 启动 | 单实例、无界面模式、主题、崩溃提示 | `App.xaml.cs` | 互斥量名按数据根目录哈希，测试副本与正式版互不干扰；无界面模式在建窗口前返回 |

| 窗口记忆 | 位置大小、列宽 | `WindowPlacementMemory` | 越界或不合理的值丢弃 |

## 六、数据设计模式

- **库分开**：`catalog.sqlite`（目录与用户偏好，唯一不能随便删的）、`search-index.sqlite`、`usage.sqlite`
  （都可重建）、`settings.json`；`archive\copies\`（来源记录的副本，来源没了它就是唯一的一份）、
  `probe-cache.json`（可删）、导入的原始数据（`gemini-web\`）。
- **稳定键**：(来源, 账号, 组织, 原生 ID)。同一实体的多份记录用列表达关系（`merged_into` 折叠、
  `continued_in` 续接、`resumed_from` 副本来源）：被折叠的行不列出但保留，用户偏好跟着转到留下的那一行。
- **增量同步**：每个源文件记（长度, 修改时间）；没变不读，变了重读；消失的只标「原记录已删」
  （`source_gone_utc`），不删行，来源回来了标记自动消失；一次没有变化的同步不写库（本项目约 0.25 s，原来 0.65 s）。
- **同步分两步**：`Read` 读来源文件、不持目录锁（读几十秒也不挡列表）；`Apply` 只做数据库里的事、持锁。
  实测列表刷新最慢一次 1085 ms → 49 ms。
- **删除只由用户发起**：删掉这一行、并入它的记录、副本和索引里的内容，同时在 `deleted_sessions` 记一条墓碑，
  以后同步时来源里还有也不再列出；来源本身不动。移除一次导入用单独的入口（按来源整批）。
- **导入的键**：同一条记录不论来自哪次导出、哪种格式，都算出同一个键（时间截到秒 + 所属对话 + 空白归一的提问），
  重复导入只补新增；来源按期限删掉的旧记录留在本机。
- **迁移加的列**：旧库里还没有的列，索引要在迁移加列之后再建（`CreateLinkIndexes`），写进建表 schema 会让旧库
  打不开；只为非空值的查询建部分索引（`WHERE col IS NOT NULL`），全量索引反而拖慢列表查询。
- **续读**：只追加的文件记 `NextOffset`；读到末尾不完整的一行就停在行首，下次接着读；文件变短或被改写就从头。
- **格式版本**：派生库用 `PRAGMA user_version` 记布局号，代码里的 `Layout` 常量一变就整库重建，
  README 写明「升级后第一次打开会重建」。
- **分页**：键集分页（上一页最后一行的排序键 + 目录修订号）；修订号变了游标作废，不会把新旧两页拼在一起。
- **撤销**：每次偏好修改记（前值, 后值, 修订号）；撤销时修订号对得上才生效，不覆盖之后的新改动。
- **偏好与源数据分开**：置顶、改名、备注、分组、归档只在自己的库；搜索也查这些字段。
- **设置里不存临时状态**：搜索框内容、组筛选不在重开时恢复（被过滤的列表看起来像丢了数据）；
  可以存「供挑选的历史」，例如最近的搜索。

## 七、界面与交互规范

- **颜色**：只用命名画刷（`WindowBrush` `SurfaceBrush` `RaisedBrush` `PopupBrush` `TextBrush` `MutedBrush`
  `FaintBrush` `SelectionBrush` `InfoBrush` …），模板里用 `DynamicResource`；深浅两套同名；标题栏跟着深色。

- **搜索**：多词同时出现、`-词` 排除、引号整句；只靠内容命中的行标出来；按相关度分段；

- **详情与预览**：选中变化后延迟约 140 ms 再读、可取消，方向键快速移动时不会每一行都去读文件。
- **长任务**：状态栏显示「正在建立索引 n/N」，完成后结果自动补全，不要求用户操作。

- **多选**：每条发言一个勾选框，Shift 连选；选中后底部换成操作栏（全选、取消选择、复制选中的 N 条、导出选中的…）；

- **弹窗**只用于需要用户决定的事；结果、成功、可撤销的操作都放状态栏。
- **设置菜单**：每个开关的提示写清会发生什么（如「关闭时索引会删除」）。
- **记住**：窗口位置与大小（含最大化）、列宽、排序（搜索时与平时各记各的）、筛选、阅读器选项。

## 八、性能与内存

**做法**

- **读大文件**：`FileStream` + 1 MB 读块，用 `IndexOf('\n')` 切行。超过 64 KB 的行先看前 8 KB 判断类型
  （工具输出、图片之类直接跳过，不先攒进内存）；一整遍共用一个行缓冲；读块和行缓冲从**有界**数组池借
  （`ArrayPool.Create(1 MB, 4)`）。别用 `ArrayPool<byte>.Shared` 装大块：它按处理器保留大数组，一遍读完会留下上百 MB。
- **后台重活**：独立线程、`ThreadPriority.BelowNormal`，几遍之间先后运行而不并发。跑完时如果自上次以来分配了
  ≥ 256 MB、且托管堆提交 ≥ 64 MB，先等 2 秒让后台线程退出、再等用户停手，做一次
  `GC.Collect(2, GCCollectionMode.Aggressive, true, true)` 把内存还给系统；每分钟再检查一次，覆盖其它重操作。
- **动画**：`RepeatBehavior.Forever` 的动画结束时要停掉时钟（`Controller.Stop()` 后移除）；只调
  `BeginAnimation(dp, null)` 时钟不会停，窗口会每秒重画 60 次。最小化或隐藏时不播放。
- **启动**：主窗口在 `OnStartup` 里自己创建（`StartupUri` 在 `Shutdown()` 之后仍会建窗口、打开整个数据库）；
  单实例转交、跳转列表、无界面模式都在建窗口前返回。
- **首屏先出**：目录为空（第一次打开）时先读最近写过的 300 份、马上列出，其余后台补齐。
- **读过的不再读**：每个文件读出的元数据连同（长度, 修改时间）存盘，读法规则改了用版本号整份作废。
- **SQL 的规模**：O(n²) 的语句（如自连接）几百行时看不出来，到几千行就是十几秒，而且期间目录锁着、列表不动
  → 给关系列加部分索引，改写成能用上索引的连接（本项目 `CROSS JOIN` 固定连接顺序）。
- **派生库别一直挂着**：ATTACH 在目录连接上的索引库被写入期间，所有目录查询慢约 10 倍（连不碰它的也慢）
  → 只在需要它的查询前 ATTACH、用完 DETACH。
- **后台模式**：读写几 GB 文件的线程进 Windows 后台模式（`THREAD_MODE_BACKGROUND_BEGIN`，CPU、磁盘、内存
  优先级一起降）；后台进度节流到每 250 ms 报一次界面。

**测量工具**（都只观察、不改程序）

- **界面卡顿**：每 50 ms 向窗口发一次 `WM_NULL`（`SendMessageTimeout`），记回应时间；同时用
  `GetThreadTimes` 读各线程 CPU，看停顿时是谁在忙、是用户态还是内核态。
- **内存**：进程私有字节与工作集每秒采样；托管堆用 `DOTNET_STARTUP_HOOKS` 注入一个只写日志的钩子
  （堆大小、各代与 LOH、累计分配、GC 次数、JIT 方法数）。
- **后台任务单独量**：写一个小控制台程序直接调用 Infrastructure，看分配量、gen2 次数、峰值和回收后的占用。
- **对照**：新旧两版同时启动并排比，交替先后顺序；机器忙闲会影响结果，跨时间比较没有意义。
- **周期性卡顿先定位再下结论**：用消息钩子查清是哪个窗口、哪条消息。本项目的「每 10 秒卡一下」最后查明是
  搜狗输入法的定时器，跟程序本身无关。
- **规模测试**：脚本生成目标规模的合成数据（本项目 3000 条、1.7 GB），用独立的数据根目录模拟第一次启动；
  宿主程序打印各阶段耗时和列表刷新延迟，并把延迟拆成「等目录锁」和「查询本身」，一眼看出是谁慢。
- **泄漏测试**：宿主程序几十轮同步、搜索、切筛选、开关各窗口，用 `WeakReference` 看关掉的窗口、换下的行和消息
  是否被回收，同时看句柄数。没 `Show` 过的窗口要真正 `Close()`，否则它留在 `Application.Windows` 里，看着像泄漏。

**参考数字**（会话管家，本机）：平时私有内存约 135 MB，其中托管堆只有 10–20 MB，其余是 WPF 与运行时；
整遍重建内容索引（约 300 份会话记录）用时视机器忙闲约 40–50 s、峰值约 300 MB，跑完回到约 130 MB；
没有变化的同步约 0.25 s；ReadyToRun 两次实测都没有收益，未采用。0.18.0 用 3000 条合成对话：第一屏 33.7 s → 2.8 s；
再启动的同步 50 多秒 → 10 秒以内；写入一次同步结果 18 s → 0.15–0.3 s；建索引期间刷新列表中位 460 → 25 ms、
最慢 3.3 s → 0.32 s；界面最长一次占用 468 → 170 ms；30 轮泄漏测试句柄数稳定在 895–903。

## 九、测试与验证

- **两个测试项目**：UnitTests（纯规则，几百毫秒）、IntegrationTests（临时目录里的真实文件与 SQLite，几秒）。
  测试名写成一句话说明行为，例如 `TypingASearchSlowlyLeavesOneEntry`；注释写为什么。
- **每个 bug**：先补能复现的测试；修好后做**反向验证**——临时去掉修复，确认测试变红，再恢复。
- **只读证明**：读前读后对外部文件算哈希和修改时间，断言不变。
- **偶发失败**：单独跑、整体跑各多跑几轮，拿到失败的测试名再下结论，不要直接重跑了事。
- **共享静态状态的测试**（例如改了全局的副本位置）放进同一个不并行的集合（xUnit `[Collection]` +
  `DisableParallelization`），否则整体跑时偶发失败。
- **测试数据里的名字**用中性占位（`ABC中期`、`C:\Users\me\`），不写真实的文件夹名、用户名、对话标题，开源时不用再改。
- **规模与泄漏**：见第八节，结论写进 README。
- **不打扰用户的验证**（按优先级）：
  1. 逻辑放进可测的类，用单元测试覆盖；
  2. **界面在内存里渲染**：小宿主程序创建普通 `Application`、合并主题字典（浅色主题用反射调用 `Theme.Apply`），
     直接 `new` 控件或窗口但**不 `Show`**；窗口的 `Content` 取出来放进一个 `Border`，补上窗口会继承给它的
     前景色、字体、字号，`Measure` / `Arrange` 后用 `RenderTargetBitmap` 存图。没有窗口、不触发 `Loaded`、
     不同步、不写任何系统状态；
  3. 必须跑真窗口时：编译到临时目录，用独立数据根目录启动，最小化启动、不激活地还原、压到最底层；
     不打开菜单和弹出层（WPF 弹出层是置顶窗口，会盖住用户的屏幕）；用户在电脑前时不做激活、二次启动之类的测试；
  4. 永远不关用户正在用的那一份；要替换时先问。
- **冒烟**：发布到暂存目录后跑一次无界面导出，确认退出码 0、全程没有窗口、导出文件更新；
  单文件版同样跑一次（把解压目录指到 D 盘）。

## 十、版本、发布与开源

- **版本号**：新功能升次版本（0.11 → 0.12），修复与性能升修订号（0.11.1 → 0.11.2）；
  同时改 csproj 的 `<Version>` 和 `app.manifest` 的 `assemblyIdentity`。
- **提交**：每完成一项提交一次，说明里写「改了什么、为什么、实测数字」；然后单独一次「x.y.z：版本号与文档」。
- **两种发布形态**：
  - 自用：`dotnet publish src/<Project>.App -c Release -r win-x64 --self-contained true -o artifacts/win-x64`
    （多文件，约 145 MB / 410 个文件，启动时不解压）；
  - 分享：`scripts/Publish-Share.ps1` → `dist/<产品>-x.y.z-win-x64.exe`（单文件约 64 MB，首次运行把 6 个原生组件
    约 10 MB 解压到 `%TEMP%\.net`）+ 同名 zip（附使用说明，给会拦截 exe 的聊天软件和邮箱）。
- **文档分工**：
  - `README.md`：给自己、维护者和 GitHub 访客——开头几行英文简介与下载链接；定位与边界、每个版本一节、界面、键盘、
    数据目录、测试与实测表、构建、分享、许可证。公开仓库里是精简版：没有「每个版本一节」和测试与实测表（用户在
    GitHub 上自己删的），导出时用脚本照样删；
  - `docs/使用说明.txt`：给最终用户，随 zip 分发——怎么用、隐私与安全、卸载；
  - `docs/capabilities.md`：给开发者——每个版本的技术说明（类名、规则、数据格式）；
  - `docs/requirements-traceability.md`：立项时的需求编号、状态与证据；
  - `evidence/`：探测与实测的原始数据（只留在私有仓库）；
  - `LICENSE`、`THIRD-PARTY-NOTICES.md`：公开时的许可证、依赖的许可证与商标说明。

**公开发布（开源）**

1. **先问清三件事**：仓库名、许可证、公开哪些提交。本项目：`session-hub`、MIT、只公开整理好的一个提交
   （私有仓库的完整历史里有本机路径和调试记录）。登录 GitHub（`gh auth login`）由用户自己完成。
2. **许可证与声明**：`LICENSE`，版权人写 GitHub 用户名；`THIRD-PARTY-NOTICES.md` 逐个列出发布物里带的依赖、版本和
   许可证（本项目：.NET / WPF、Microsoft.Data.Sqlite 为 MIT，SQLitePCLRaw 为 Apache-2.0，SQLite 为公有领域，
   ZstdSharp.Port 为 MIT），再写商标说明「不是 Anthropic、OpenAI 或 Google 的产品」；README 开头加几行英文简介和
   下载链接（`../../releases/latest`）。
3. **去个人信息**：用一个替换脚本，统一改掉源码注释、测试、文档里的本机用户名、文件夹名、姓名缩写和真实对话标题，
   换成同样形状的占位名（测试照样测原来的东西）；删掉带本机路径的 `evidence/`；全仓库再扫一遍。
4. **只公开整理好的提交**：`git archive HEAD` 导出到一个干净文件夹 → 从头构建、跑全量测试 → `git init`，作者用
   GitHub 的 noreply 邮箱（`<id>+<用户名>@users.noreply.github.com`），提交一次 → `gh repo create <名字> --public
   --source . --push`。
5. **署名**：公开仓库的提交说明不加 AI 的 `Co-Authored-By`（GitHub 会把它列进贡献者）；几家 AI 都参与时，在 README
   里写一句「由 ChatGPT、Claude、Gemini 辅助构建」。
6. **Release**：资产用英文文件名（中文文件名会被 GitHub 换成点），中文写在资产标签和说明里；说明里附 SHA-256，
   发布后用 API 返回的 `digest` 核对。几十 MB 的文件经本机代理上传可能被断开：先建草稿，逐个上传、失败隔一会儿
   再试，全部传完再发布。
7. **上传前查二进制**：单文件 exe 是压缩的，按字节搜不到不代表没有；要核对改掉的名字只出现在注释里（不会编进程序），
   并检查 zip 里的说明文件。
8. **以后的版本**（0.23.0 起这样做）：
   - 先在私有仓库清理上次公开以来新增内容里的个人信息（如测试里用到的本机部署目录名），单独提交：两边的源码树
     始终一致，下次导出不用再改；
   - 公开文件夹先 `git fetch` 并快进：用户可能直接在 GitHub 网页上改过（本项目改过 README）；从不强推；
   - 清空公开文件夹里受版本控制的文件，解出私有仓库的 `git archive HEAD`，README 换成脚本生成的精简版——脚本先拿
     上一版的 README 试，要能一字不差地还原用户在网页上的修改；再逐个文件核对：除 README 外和私有仓库一模一样；
   - 在公开文件夹里从头构建、跑全量测试，然后提交（noreply 作者、不加 AI 署名）、推送；
   - 发布包也在公开文件夹里构建：程序里嵌的版本号（`0.23.0+<提交>`）就是公开仓库里查得到的那个提交；冒烟测试，
     并和私有构建在同一份数据上的结果比对；
   - Release 照第 6 条：草稿、逐个上传带重试、核对 `digest`，再发布并设为最新。

## 十一、与 Claude 协作的工作方式

## 十二、新项目规划模板

每个阶段的固定动作：开工前写清范围 → 做完跑全量测试 → 实测 → 提交 → 文档 → 发布。

### 阶段 0　立项与边界（约 1 天）

- 一句话定位，加「只做两件事」式的范围；
- 读写边界：读哪些、写哪些（只写自己的数据根目录）；
- 数据源清单：每个源的位置、格式、规模、会不会正被别的程序写入或清理；
- 需求编号 R01…，每条带验收标准；
- 能力矩阵（默认全部 Unknown）；
- P0 只读探测脚本，产出 `evidence/*.json`；
- 确认技术栈（默认用附录的）。

**退出标准**：每个数据源至少有一份真实样本被探测脚本读通；边界写进 README 第一段。

### 阶段 1　骨架（0.1，2–3 天）

- 建 slnx、三个源码项目、两个测试项目（`Wire-Projects.ps1` 一键配好目标框架、引用和包）；

- 发布脚本、启动时间测量脚本；需求追溯表。

**退出标准**：真实数据能列出来；只读证明测试通过；`artifacts` 里的程序双击能用。

### 阶段 2　可用（0.2–0.5）

增量同步、键集分页、排序与分段、筛选、详情面板；阅读 / 预览窗口（流式读取，可从末尾先读）；

**退出标准**：自己每天用不卡、不丢；每个功能有测试；README 每版一节。

### 阶段 3　好用（0.6–0.9）

全文索引（FTS5）、统计账本、导出（Markdown / 自包含 HTML / CSV）、无界面模式（导出、生成草稿）、

**退出标准**：几百条数据里 1 秒内找到要的东西；导出的文件可以单独发给别人。

### 阶段 4　打磨（0.10 以后）

性能与内存的量化优化、同一实体多份记录的合并规则、边角格式（坏行、半行、超长行、编码）、
分享包与使用说明、最近的搜索这类顺手功能；只加不减（副本、墓碑）；导入用户的导出包；
目标规模的首次打开（先列最近的一批）与泄漏测试。

**退出标准**：实测数字进 README；分享包在没装 .NET 的机器上能用；来源删掉的记录照样能看。

### 阶段 5　公开（可选）

许可证与第三方声明、去个人信息、干净目录从头构建与测试、一个提交的公开仓库、带 SHA-256 的 Release（见第十节）。

**退出标准**：别人照 README 能下载运行，也能从源码构建、跑通全部测试；仓库里扫不到本机用户名和路径。

## 十三、换一种软件：概念对照

| 会话管家里的 | 新软件里换成 | 例：田间调查数据管家 |

| 数据源（Claude、ChatGPT、Gemini 的记录目录） | 产生数据的程序、仪器或共享文件夹 | 扫描的调查表 PDF、照片、Excel 记录表所在的文件夹 |

| 置顶、改名、备注、分组、归档 | 同样，只存自己的库 | 标注「已复核」「待重测」，按试验分组 |
| 内容索引 | 全文或字段索引 | 按材料编号、品种名、备注搜索 |
| 用量账本 | 汇总账本 | 病情指数、抑制率、均值与标准差的汇总 |
| 阅读窗口 | 预览窗口 | 原始表格图片与提取结果并排对照 |
| 导出 | 报表导出 | 带公式的 Excel、HTML 报表 |
| 在 Claude / ChatGPT 中打开 | 用外部程序打开 | 用 Excel、R、浏览器打开原文件 |
| 改动的文件 | 变更历史 | 某份数据被修订过几次、改了什么 |

**如果新软件必须写外部数据**（会话管家刻意没有）：写入集中到一个模块，并且——

- 先过门禁：用可丢弃的数据在真实环境实测通过，能力矩阵标 Verified 才开放；
- 写之前自动备份到自己的数据根目录，写之后读回核对；
- 先预览（干跑）再执行，执行要用户明确点确认；
- 记录每次写入（时间、对象、前后值），提供还原；
- 对方程序正在运行或文件被占用时拒绝写入，并说明原因。

## 十五、踩过的坑

**WPF 与 Windows**

- `App.xaml` 里写了 `StartupUri` 时，即使启动代码已经 `Shutdown()`，WPF 仍会建主窗口、打开整个数据库 →
  不写 `StartupUri`，在 `OnStartup` 里自己 `new`。
- 在宿主程序里 `new App(); InitializeComponent()` 会把 `StartupUri` 一起带出来，在用户屏幕上弹出整个主窗口 →
  宿主用普通 `Application` + 合并主题字典。
- WPF 弹出层是置顶窗口 → 测试副本里不要打开菜单和下拉。
- `BeginAnimation(dp, null)` 不会停掉无限循环的动画时钟 → 窗口持续每秒重画 60 次。
- `Process.CloseMainWindow` 关的是 .NET 认定的「主窗口」，开着阅读窗口时关的是阅读窗口 →
  对标题为「<产品>…」的列表窗口发 `WM_CLOSE`（程序用 `ShutdownMode=OnMainWindowClose`）。
- 后启动的测试副本即使压到最底层也可能拿到前台 → 启动后把焦点交还；用户在电脑前时不做这类测试。
- 跳转列表由 Windows 保存在 `%APPDATA%\Microsoft\Windows\Recent\CustomDestinations`（C 盘）；
  单文件版把原生组件解压到 `%TEMP%\.net`。如果用户在意 C 盘，提前说明。
- 输入法（搜狗拼音）在界面线程上跑每 10 秒一次的定时器，偶尔每次占几百毫秒内核时间 → 先定位再归因。
- 文本框里的 Ctrl+Z 应该留给「撤销输入」，全局撤销只在不编辑时生效。

**.NET 与内存**

- `ArrayPool<byte>.Shared` 按处理器保留大数组；`JsonDocument` 也从共享池租缓冲，线程各留一份，线程退出后才释放。
- 垃圾回收器释放的内存默认留着备用，程序空闲时不再回收 → 重活之后、用户停手时做一次 Aggressive 回收。
- 回收要等后台线程真正退出（先等 2 秒），否则线程自己留的缓冲还活着。
- `Enum.TryParse` 接受任意数字 → 再用 `Enum.IsDefined` 检查，否则设置里的 "7" 会变成不存在的列。

**数据与格式**

- 对方正在写的文件：最后一行可能只写了一半 → 停在行首，下次再读。
- 超长行（工具输出、内嵌图片）：先看开头再决定读不读；消息行放宽上限，免得连文字一起丢掉。
- 被截断成半个的表情（孤立的 UTF-16 代理项）只能损失这一个字符，不能让整份记录读失败。
- 同一句话可能被写两遍（不同事件类型）→ 按内容哈希配对去重，但真正重复说的话不能被误合并。
- 项目搬过目录会留两份同 ID 的记录 → 取最后写入的那一份。
- SQLite 连接不是线程安全的 → 所有调用经一个门（`SemaphoreSlim`）。
- FTS5 trigram 至少要三个字符 → 两个字的词走 `LIKE` 扫描（慢一些，约 0.17 s）。
- 新列上的索引写进建表 schema → 旧库还没有这一列，打开就失败：迁移加列之后再建。
- 同步时「来源里没有了」→ 可能是被清理、被挪走、被别的工具压缩，不等于用户想删：只标记，不删。
- 别的工具会压缩应用的记录（如把 rollout 压成 `.jsonl.zst`）→ 应用自己都找不到；认得压缩格式，压进自己的副本再读。
- 对话记录八成是内嵌的 base64 图片，NTFS 压缩只省一成；zstd 开长距离匹配、在一大帧里找重复发过的图，能压到三分之一
  → 帧要够大（32 MB），读的时候靠寻址表只解要的那一帧，不用整份解压。
- 随机读压缩文件，每放大一次读取窗口都从帧头重解一遍 → 随机读时整帧解进缓冲，同帧再读不再解；缓冲放在非托管内存、
  关闭即还，不留给垃圾回收。
- 清单里记的是绝对路径：数据目录搬过家（或被复制去测试），清单还指着旧位置，按旧路径删文件会删到别处 → 只在自己的
  文件夹里写和删，指向别处的先在本地按同名找。
- 文件换了个名字（明文副本压成 `.zst`）≠ 内容变了 → 索引、账本按路径记的，同名加后缀且长度相同就只改路径，不重读几 GB。
- ChatGPT 的导出里一段对话是一棵树（改提问、重新生成都是分支）→ 从 `current_node` 沿父节点回溯；直接遍历全部节点会把
  放弃的分支也列出来。大的导出把对话拆成好几份编号的文件 → 认 `conversations*.json` 全部。
- 拿不到真实样本的格式（第三方的导出）→ 按公开格式容错地写：认不出的部分计数报告，不让整份导入失败；选错了别家的导出要说出来。
- 同步每次都整份解析几千个导入文档的表头 → 自己写的文档把表头字段放在正文前面，只读开头几十 KB。
- 导出包里的时间写的是导出时所在的时区（如 EDT）→ 按导出里写明的时区换算，JSON 和 HTML 两种格式才对得上。
- 导出包里附件的扩展名可能被改（jpg 存成 png）→ 找不到时按同名换扩展名再找。
- 自连接之类的 O(n²) 语句只在几千行时显形；ATTACH 的库被写入时拖慢所有查询 → 都只有在目标规模下才量得出来。

**测量**

- 环境噪声很大（别的程序占满内存、输入法、杀毒扫描），跨时间比较会得出错误结论 → 新旧并排、交替顺序。
- 挂上采样器之后问题「消失了」，不一定是采样器干扰，也可能只是那段时间恰好没发作 → 多跑几轮、看时间分布。
- 泄漏测试里没 `Show` 过的窗口，用反射调 `OnClosed` 不等于关掉，它还留在 `Application.Windows` 里 → 用真正的 `Close()`。

**GitHub 与发布**

- 提交说明里的 `Co-Authored-By: Claude …` 会让 GitHub 把 Claude 列进贡献者 → 公开仓库的提交不加，署名写在 README。
- 版权人、提交作者写成邮箱前缀会暴露邮箱 → 用 GitHub 用户名和 noreply 邮箱。
- Release 资产的中文文件名会被换成点 → 英文文件名 + 中文标签。
- 经本机代理上传几十 MB 的文件可能被断开，`gh release create` 带资产失败时会撤掉整个 Release → 先建草稿，逐个上传、带退避重试。
- 公开仓库不只有自己在改：用户在 GitHub 网页上删过 README 的两大段 → 导出前先 fetch 快进，看清别人的改动，
  照样保留（本项目写成生成精简 README 的脚本），绝不拿本地的旧树覆盖、不强推。
- 发布包在私有仓库里构建时，程序里的版本号带的是私有提交，公开仓库里查不到 → 在公开文件夹里构建。
- 上次公开以来新增的测试和实测记录里，又出现了本机的目录名 → 每次公开前都对这一段改动重新扫一遍个人信息。
